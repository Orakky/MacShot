# ADR-008 遮罩实现：整屏冻结快照 + 全屏透明窗（不做实时流）

状态：**accepted**（用户 2026-11-16 签字："采集的时候冻结快照，暂时不需要考虑实时"） 相关：ADR-007、FR-CAP-001、FR-SESS-004

## 背景
"按下热键后背景不动"是 Snipaste 类工具的核心手感（选区期间内容变化会拖不住边缘）。注意事实边界：**Snipaste 官方文档没有"冻结屏幕"这一措辞**，只能从其有 `F5 Refresh screenshot` 与历史回放推断首帧已冻结（`docs/reference/snipaste-gap.md` §3）。所以这条是我们的设计选择，不是"抄作业"。

## 决策（建议）
1. 会话开始时抓**一整帧**（单屏，见 Q-09），遮罩窗绘制的就是这张位图；选区只是位图上的一个矩形，裁剪从它上面做（`CGImage.cropping`，无重采样）。
2. 会话期间不再回源屏幕（一条会话 = 一次采集）。
3. 显示器布局与会话开始时的快照绑定（`LayoutSnapshot`）。
4. 遮罩绘制用 4 块暗化矩形拼"洞"，不用 even-odd 整层（脏区性能）。

## 已考虑并否决的方案
| 方案 | 否决理由 | 什么证据会翻案 |
|---|---|---|
| 实时预览（SCStream 常驻） | 背景会动 → 选区跟不住；常驻功耗与内存；四大件不需要 | 若需求变成"实时选区里挑窗口/元素预览"，那是 P1 `FR-CAP-011` 的另一套方案（ADR-017） |
| 透明遮罩不回源（只叠半透明层，底下还是真屏幕） | 最省内存，但"背景不动"与"裁剪像素与屏上一致"两条都做不到；且鼠标划过控件会改背景 | 不会 |
| 逐显示器分别抓取后再拼接 | 跨屏选区（P2）才需要；P0 多花的复杂度没有收益 | Q-09 改选 B 时启用 |
| 抓两次（预览一次、提交一次） | 会出现"框到的和拿到的一样吗"这一无法回答的问题 | 不会 |

## 后果
正面：FR-CAP-001/008 与 FR-SESS-004 变成实现属性；裁剪路径唯一。
负面：整屏一帧在 4K 上约 33MB（**待实测**），会话期内存峰值抬高；退出会话必须释放。
风险：抓取时机在遮罩显示**之前**，所以遮罩出现延迟 ≈ 采集耗时 —— 这正是 `t.hotkey→frozen` 必须实测的原因（不能靠事后优化）。

## 判据
1. 播放动画时截图，遮罩内背景全程不变（实拍 `V-00x`）。
2. 会话内拔屏不崩、结果与快照一致（`V-011`）。
3. 会话结束后帧被释放（内存读数回到基线）。
